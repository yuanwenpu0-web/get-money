# 性能优化记录（2026-10-27）

批量行情、资金费和巡检增量同步共用有界线程池：默认最多 8 路网络请求，跨币种及分页复用 HTTP 连接，每个工作任务最多缓冲一页。所有 ORM 查询、写入和回滚留在调用线程，兼容 SQLite 的单写事务限制；一个币种失败后其余任务继续，错误按输入顺序返回。

高周期尾部查询从最新原始分钟定位所需窗口，缺少有效桶时向历史扩展，保留缺分钟排除和 as-of 查询的原有结果。K线 API 先读取数据，空结果时才触发同步，省去额外的最新时间聚合查询。

巡检中同一币种的策略共享K线、资金费和基础特征，只有多周期策略计算 MTF；缓存只保留当前序列，每轮巡检重新创建引擎。开仓资金核算、持仓管理与交易执行仍按原顺序处理。周期返回值和日志新增 `sync_ms`、`signal_ms`、`execution_ms`，便于定位运行中的耗时。

自动训练按币种并行，每任务独立数据库会话；默认 2 个任务，上限同时受配置、目标数及 `CPU逻辑核数 // 2` 限制，因为每个模型内部已有 2 个计算线程。内存 SQLite、共享 StaticPool 和绑定 Connection 的会话自动串行。模型评估复用一次概率推理，避免重复遍历树；模型文件名加入微秒。

账户历史统计改为 SQL 聚合，避免加载所有平仓订单。行情首屏中的来源、币种和图表请求并行；订单和总览页面最多执行一轮刷新，进行中新增的刷新合并为下一轮，卸载后停止排队。

## 并发配置

| 配置 | 默认 / 范围 | 生效方式 |
| --- | --- | --- |
| `MARKET_SYNC_WORKERS` | 8 / 1–32 | 根目录 `.env` 环境变量，重启后端；用于行情、资金费批量同步及巡检增量同步 |
| `auto_train_workers` | 2 / 1–8 | 设置页“自动训练并发数”或 `PUT /api/settings`，下一轮自动训练生效；实际还受 CPU 预算限制 |

设置为 1 可降低对应链路的并发。历史同步任务依然通过同步 HTTP 请求返回，窗口较长时需要等待分页完成。

## 离线基准

脚本仅使用临时内存 SQLite、合成K线/订单和模拟网络，不连接交易所或业务数据库，不生成模型文件。每项均断言优化前后数据或信号完全一致，速度不作为测试通过条件。保存的实测值见 [performance-benchmark.json](performance-benchmark.json)。

| 场景 | 比较路径 | 本次耗时 | 加速 |
| --- | --- | --- | --- |
| 24 币种，每次网络模拟延迟 30ms | 1 worker → 8 workers | 757.3ms → 144.7ms | 5.23 倍 |
| 216,000 分钟取 400 根 1h | 全历史聚合 → 尾部窗口聚合 | 258.9ms → 27.9ms | 9.26 倍 |
| 24,000 分钟、同币种 5 个策略 | 分别构建特征 → 单轮共享特征 | 281.3ms → 104.6ms | 2.69 倍 |
| 20,000 笔平仓订单统计 | ORM 全加载 → SQL 聚合 | 559.9ms → 6.6ms | 85.11 倍 |

行情同步各测一轮；其余各测 5 轮，报告中位数并保留所有样本。信号测量包含实际K线读取和指标计算，`save=False`，不含信号写入。这些数字只反映所列局部负载，不能直接相乘或视为完整交易周期的加速。

从项目根目录复现：

```powershell
.\.venv\Scripts\python.exe backend/scripts/benchmark_performance.py --output docs/performance-benchmark.json
.\.venv\Scripts\python.exe -m pytest backend/tests -q
cd frontend
node --test tests/request-concurrency.test.mjs
npm run build
```
