- 判定合计：`no_trades 938 / insufficient 98 / inconclusive 68 / negative 20 / **pass 0**`
- 逐币最佳周期：`1h 417 / 15m 51 / 4h 30`（498 个币有结果）
- 498 个币里，验证段为正且 ≥3 笔的只有 **17 个**，且全部 `inconclusive` 或 `insufficient`

一句话：**换周期、换参数都不制造 edge，只是把「信号太少」和「信号为负」对调。**

## 二、这次配置改了什么

用户诉求是「把这个策略允许的币种范围改成全部」。查下来「范围」不是一层，是四层：

```
交易所 U 本位永续（500+）
  → symbol_scope             原来已是 all ✅
  → min_quote_volume_usd     原来是 3000 万美元 ❌ 这一步把宇宙砍到 67 币
  → symbol_blacklist         6 个币
  → 池规则                    原来绑定 major(16) / alt(49)
  = 实际范围
```

实际改动：

| 项 | 改前 | 改后 | 影响 |
| --- | --- | --- | --- |
| `min_quote_volume_usd` | 30,000,000 | **0**（不过滤） | 宇宙 67 → 509 币 |
| 绑定 #1 | `major × 15m` | **`all × 15m`** | 16 → 509 币 |
| 绑定 #2 | `alt × 5m` | **`all × 5m`** | 49 → 509 币 |
| 绑定 `enabled` | 0 | **0（未动）** | 只换范围，不改变是否上线 |

同时补了两个配套（否则下次还会对不上账）：

- `GET /api/market/symbols` 回传 `count` / `min_quote_volume_usd` / `blacklist`，设置页直接显示「当前实际生效 N 个合约」，流动性门槛做成可编辑输入。
- `scripts/set_strategy_scope.py`：幂等改范围，带 `--dry-run`，撞唯一键跳过而不是抛错，**默认不动 `enabled`**。

> 注意：寻优的币种范围走的是另一条口径——`symbol_universe()` 直接按 `klines` 覆盖度算，不受池与流动性门槛限制。所以「回测扫了 1053 个任务」和「池里 509 个币」本来就是两套数字，前者是「该周期历史够长的币」。

## 三、数据边界（决定能跑什么）

| 周期 | 365 天可用币 | 90 天可用币 | 瓶颈 |
| --- | --- | --- | --- |
| `5m` | **0** | 71 | 只能由 1m 聚合，1m 仅覆盖 90 余天 |
| `15m` | 57 | 100 | 461 个币 2026-10 才开始采 |
| `1h` | **499** | 518 | 唯一原生覆盖满一年 |
| `4h` | **499** | 518 | 由 1h 派生补齐（`derive_candles.py`） |

所以「5m 也要动态」只能在 90 天窗口里做。**5m 的结论不能和 365 天结果横向比**，两者窗口不同。

## 四、方法

- 网格来自 `StrategySpec.grid`：7 键 972 组，本次按均匀下标抽 **64 组**（比上一轮 32 组翻倍），强制包含线上基准组合，逐组合过 `resolve_params` 过滤非法档位。
- 前 70% 训练段选参（目标 `净收益 + 0.5×最大回撤`），后 30% 验证段**只判定不选参**。
- 判据：成交笔数达标 + 验证段为正 + 每笔期望 95% CI 不跨 0。
- 进程池按 `(币种, 周期)` 分片，20 进程；BLAS 线程压到 1。
- 池化层有 `MIN_POOLED_TRADES = 30` 门槛，样本不足只给数值不给结论。

**性能**：365 天批次 1053 个任务 **578 秒**（0 失败），5m 批次 71 个任务 **148 秒**。合计 1124 任务 / 约 12 分钟。比上一轮（32 组 / 322 秒）慢约 1.8 倍，符合「组合数翻倍 × 帧更长」的预期。

## 六、比「哪个币最优」更有用的：参数偏好

172 个有候选组合的任务里，最优组合相对线上基准改了哪些键、改成什么：

| 参数 | 线上基准 | 被改动比例 | 首选值（次数） | 读法 |
| --- | --- | --- | --- | --- |
| `conf_mode` | 1（开确认状态机） | **93.0%** | **0 × 160** | 确认状态机是头号瓶颈：开着它，绝大多数币根本没有信号 |
| `delta_pct` | 95 | **87.8%** | **90 × 150** | 需要放宽吸收强度门槛才能凑够信号 |
| `sl_buffer_atr` | 0.25 | 75.0% | 0.15 × 67 / 0.4 × 62 | 两极分化，没有一致方向 → 这个键基本是在拟合噪声 |
| `target_r` | 2.0 | 68.0% | 3.0 × 74 / 1.5 × 43 | 略偏「高盈亏比」 |
| `min_score` | 0.55 | 65.7% | 0.7 × 62 / 0.8 × 51 | 少而精：宁要更少更强的信号 |
| `be_trigger_r` | 1.0 | 51.2% | **0.0 × 88** | 一半的币上「1R 保本」是负贡献，关掉更好 |
| `max_hold_bars` | 30 | 50.0% | 45 × 46 / 60 × 40 | 需要更长的持有窗口让 3R 目标可达 |

方向是一致的：**放宽入场（关确认 + 降 delta 门槛）、收紧评分、拉长持有、提高目标**。翻译成人话——这个策略当前的参数设置太严，导致样本极少；一放宽，成交变多，但期望收益仍然为负。这说明问题不在参数配比，而在信号本身的预测方向。

`sl_buffer_atr` 的 67/62 对半分是个明确的反向信号：**这个键的最优值随币种随机漂移，属于过拟合**。如果要继续用这个策略，这个键应该固定在基准值上，不要放进搜索空间。

## 七、结论与下一步

1. **参数寻优不能制造 edge**。这次把范围放到 509 币、周期放到 4 个、组合数翻倍到 64，`pass` 仍然是 0。前几轮（P0–P10）关于「现货 OHLCV 价格序列没有可提取信号」的结论继续成立。
2. **5m 是最差的（−0.33%/笔，CI 全负）**，15m 次差，1h 不确定，4h 样本太少。周期越短越负，说明成本项（手续费 + 滑点 0.06%）在吃掉本来就微弱的均值回归。
3. **1h 是唯一「不算负」的口径**（+0.067%/笔、122 笔），但 CI 跨 0 且宽度达 0.8 个百分点——要有结论需要 10 倍以上样本量。
4. 参数偏好给出了明确的重构方向，而不是调参方向：**问题在 `conf_mode` 这套确认状态机的设计**（93% 的币要靠关掉它才有交易），以及信号层缺失。继续调 `sl_buffer_atr` / `target_r` 只会过拟合。
5. 已算出的每币最佳参数**没有写库**（`pass=0`，写进 `symbol_params` 等于用噪声覆盖线上）。要应用请自己在「寻优」页按门槛筛选后点应用，或在命令行：

```bash
# 复现本次结果（不写库、不改线上）
python backend/scripts/optimize_all.py --intervals 15m,1h,4h --days 365 --combos 64 --min-trades 3 --out data/opt365
python backend/scripts/optimize_all.py --interval 5m --days 90 --combos 64 --min-trades 3 --out data/opt5m
```

## 八、边界与已知问题

- **5m 只有 90 天**：1m 历史从 2026-07-27 起，5m 只能聚合这么多；365 天窗口下 5m 可用币数为 0。要拉长 5m 必须补 1m 历史。
- **4h 是派生数据**：由 1h 聚合、桶内不足 75% 根数丢弃。1h 历史短的币 4h 也短，所以 4h 在 30 天窗口只有 99 币、365 天有 499 币。
- **`no_trades` 占 84%**（938/1124）：不是参数不好，而是信号太稀疏。BTC 一年在 1h 上只命中 5 次、4h 上 0 次——门槛过不去就不该硬选一套参数。
- **delta 口径**：1m 覆盖不足的区间逐根回落 est delta，`mixed` 表示两者混用。这保证了长窗口能跑，但前后半段的信号密度不一样，跨期可比性弱于纯 lower。
- **本次未做的事**：跨区间稳定性二次筛选（同一组参数在滚动窗口里是否稳定）、交易成本敏感性、按流动性分层看结果。这些会放进下一个策略的评估流程，不再在吸收反综上追加。
